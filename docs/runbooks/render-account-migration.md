# Safe Render account migration

Stashr cannot transfer an existing Render service object between workspaces. This workflow recreates the service under the destination Render account, updates connected frontend environment variables, transfers custom-domain mappings, verifies the replacement, relinks the project, and only then permits deletion of the original service.


The Deployments table's Render account selector opens this migration workflow and preselects the chosen destination account; it does not simply rewrite the project's account reference. The generic `/deploy-ops/.../account` route explicitly rejects Render reference-only switches. The old service remains intact until the destination is configured, deployed, relinked, and the user confirms the final deletion step.

## Workflow

1. **Plan:** Check the source service, destination account/workspace, direct environment variables, direct secret files, linked Render Environment Groups, connected frontend URL references and custom domains. For custom domains the wizard performs a read-only DNS preflight (CNAME, A and AAAA lookups) and shows the destination Render hostname. The old service remains untouched.
2. **Create and configure:** Create a replacement using the same repository, branch, supported build/start settings, region/plan, direct environment variables and direct secret files. Copy each linked Environment Group to the target workspace and link the copied group only to the replacement. Environment groups with workspace-specific `environmentId` values are flattened into a destination workspace-level group; review this scope difference. After group copying, request a fresh deploy so the replacement starts with all group values.
3. **Update connected frontends:** Replace references to the old generated Render hostname in selected connected Render services and linked Vercel, Netlify, Railway or Cloudflare Pages environment variables. Stashr automatically redeploys selected frontends through their connected provider APIs. Provider-hidden secrets and variables outside the connected targets are not readable. A failed variable update or redeploy must be retried before continuing.
4. **Transfer custom-domain mappings:** Add the source service's custom domains to the replacement. If Render returns a conflict because a domain is still attached to the source, the wizard releases that domain from the source and retries the add; if reattaching fails, it attempts to restore the old mapping and reports the handoff for manual inspection.
5. **Update DNS and verify:** DNS is managed by the domain's DNS provider, not the Render service API. For subdomains (such as `www`), update the CNAME to the new `.onrender.com` hostname. For root/apex domains, follow Render's provider-specific instructions—typically A record `216.24.57.1` or ALIAS/ANAME; Cloudflare uses CNAME flattening. Remove conflicting AAAA records because Render currently uses IPv4. The wizard reads CNAME/A/AAAA records but never changes them automatically. After DNS changes propagate, run Render domain verification and manually test the domain.
6. **Verify traffic and relink:** Open the replacement and a frontend, exercise a real request, and confirm the request reaches the new service. The project link is not switched until the replacement deployment is live and every expected custom domain reports verified.
7. **Delete source last:** The backend refuses deletion unless the project has been relinked through the wizard, the replacement is live, all expected custom domains are verified, the old generated URL no longer appears in readable environment variables of connected Render services, and the exact old service name is confirmed.

## Return to the original account

The first successful migration records the original Render account in the encrypted project metadata. On a later migration, the wizard offers **Return to original account** when that account is still connected. It runs the same replacement, frontend-update, domain-verification and old-service safeguards in reverse. Keep the old service until the reverse migration is verified.

## Important boundaries

- The Render API provides custom-domain add/list/verify/delete operations; it does not edit DNS records at an external provider. Domain mappings are automated, but DNS edits remain manual unless a separately authorized DNS-provider integration is implemented.
- A domain marked verified on the old service does not by itself mean requests are routed to the new service. The DNS target and the new Render service's domain mapping both need to be correct.
- If your custom domain is attached only to the Stashr client/static site, it does not move during a backend migration and no backend DNS change is needed. The wizard skips its backend DNS step when the backend has no custom domains; it updates the client's readable API environment variable and redeploys the client, leaving the client service and its domain in place.
- The workflow copies the web/static service configuration, direct environment variables, direct secret files, and linked Environment Groups. It does **not** migrate database contents, Redis/Key Value data, external provider resources, or persistent-disk data; persistent-disk services are blocked. Keep source databases/resources available and plan data migration separately.
- The workflow rewrites readable old-URL references in connected Render service variables/secret files/environment groups and linked provider variables. URLs hard-coded in source code, hidden provider secrets, configuration files outside those targets, third-party callers, and bookmarks are not automatically rewritten.
- Selecting a shared Render Environment Group changes every service linked to that group, not just the moved service. Review the UI's shared-group warning before applying such updates.
- The old service's `.onrender.com` address cannot keep forwarding after the old service is deleted. Use a stable custom domain for callers that need an address across migrations, or keep a deliberate proxy/redirect service at the old address.
- Render's custom-domain instructions: [Custom domains](https://render.com/docs/custom-domains), [Other DNS providers](https://render.com/docs/configure-other-dns), and [Cloudflare DNS](https://render.com/docs/configure-cloudflare-dns).
